# 플레이테스트 기록 작성 규약

기록 형식 v1. 경제 시뮬레이터의 외부 선택 모드에서 사람 또는 LLM이 판단한
플레이를 반복해서 기록할 때 사용한다. 목적은 다른 세션과 개발자가 **무엇을 보고,
어떤 이유로 선택했고, 실제로 무엇이 달라졌는지** 추적하고 비교할 수 있게 하는 것이다.

[복사용 템플릿](templates/manual-playtest.md)을 사용하고 실행 방법은
[경제 시뮬레이터](economy-simulator.md)를 따른다. 이 규약은 문서·증거의 형식이며
게임 밸런스 합격선이나 특정 구매 전략을 정하지 않는다.

## 1. 파일 이름과 위치

- 실행마다 `YYYY-MM-DD-NN` 실행 ID를 부여한다. 날짜는 테스트 시작일의
  `Asia/Seoul` 기준, NN은 같은 날의 01, 02, … 순번이다. 먼저 기존 기록을 확인한다.
- 본문: `docs/history/manual-playtest-YYYY-MM-DD-NN.md`.
- 증거 폴더: `docs/history/manual-playtest-YYYY-MM-DD-NN-data/`.
- 실행 ID가 같아도 시드·설정·소스를 바꾸거나 새 게임을 시작하면 별도 실행으로 기록한다.
  입력 재생 검증 역시 원본과 다른 실행 ID를 쓰고 원본을 참조한다.
- 날짜를 넘겨 계속한 실행은 시작 ID를 유지하고 시작·종료 시각을 각각 기록한다.
- 완료·중단 기록 모두 `docs/history/README.md`에 링크한다. 성공한 실행만 보존하지 않는다.
- 기존 `manual-playtest-2026-09-14.md`는 규약 도입 전 기록이다. 원래 이름과 원문을
  유지한다. 새 템플릿을 과거의 사전 기록인 것처럼 소급 적용하지 않는다.

## 2. 테스트를 시작하기 전에

템플릿의 실행 정보·검토 질문을 먼저 채운다. 최소한 다음을 남긴다.

| 항목 | 작성 기준 |
|---|---|
| 형식 버전·실행 ID | `v1`, 고유 실행 ID |
| 시각 | 시작·종료 ISO 8601 시각과 시간대. 미기록이면 `미기록` |
| 대상 소스 | 실행한 전체 Git commit SHA. 기록을 저장한 커밋과 구분 |
| 작업 트리 | clean 여부. dirty면 실제 변경 patch와 미추적 입력도 증거로 보존하고 해시 기록 |
| 환경 | Godot 버전, OS, headless/화면 입력 여부, 고정 틱, 실행 명령 |
| 판단 주체·사전 지식 | 사람/LLM 및 확인 가능한 모델·설정, 기존 플레이·소스·이전 결과를 봤는지 |
| 관측·거래 설정 | 실제 적용된 config 전체, 시드, 관측 품질/확률, 자동 장비, 구매 전략 |
| 초기 상태 | 새 게임/기존 상태, 자원·연구·모듈. 기존 상태는 재현에 필요한 입력도 보존 |
| 종료 기준 | 전체 연구 완료/지정 구간/시간 제한 등. 사람의 종료·포기도 별도 이유 기록 |
| 검토 질문 | 예: 분열 해금 이후 한 경계에 몇 개를 구매하게 되는가? |
| 비교 대상 | 이전 실행 ID와 바꾼 조건. 없으면 단독 탐색 실행이라고 명시 |

완전히 블라인드였다고 주장하려면 실제로 접근한 정보 범위가 그 주장과 맞아야 한다.
같은 세션에서 구현이나 이전 결과를 이미 읽었다면 공개 state만으로 명령을 골라도
초견 테스트라고 부르지 않는다. 알 수 없는 모델 세부 설정이나 시각을 추정해 채우지 않는다.

실행 중 새로운 정보·소스·진단 report를 읽거나 전략을 바꾸면 해당 판에 적는다.
최종 report 같은 내부 진단은 공개 state와 구분하며, 초견 판단을 원한다면 종료 후 읽는다.

## 3. 반드시 지킬 기록 순서

1. **공개 상태 수신:** 원본 `state`를 보존한다. revision·관측 시간·자금·표본·연구·
   보유/장착 모듈이 어떤 상태였는지 연결할 수 있어야 한다.
2. **행동 전 기록:** 보낼 명령과 짧은 판단 이유를 먼저 저장한다. 목표, 고려한 대안이나
   보류 이유, 기대 변화 중 선택을 설명하는 것만 적는다. 상세한 내부 사고 과정은 요구하지 않는다.
3. **명령 실행:** 저장한 명령을 현재 revision으로 보낸다. 수정했다면 원래 기록을 지우지
   말고 취소/수정 기록과 새 명령을 추가한다.
4. **결과 수신:** `result`와 새 `state`를 덧붙인다. 성공·실패, 자원 변화, 실제 뽑기 결과,
   장착 교체와 해금을 기록한다. 예상이 틀려도 사전 이유를 결과에 맞춰 고치지 않는다.
5. **경계 마무리:** 다음 판으로 갈 때 저축·구매 종료·장착 보류 이유도 기록한다.

한 번에 여러 명령을 골랐다면 묶음 전체의 이유를 실행 전에 기록해도 된다.
단, 각 명령의 전후 state와 결과를 보존하고, 다음 결과를 본 뒤 새로 고른 행동은
새 판단 기록으로 남긴다. 'A 대신 B' 같은 대안은 실제 고려했을 때만 적는다.

문서는 나중에 로그에서 생성해도 된다. 그 경우 **문서 작성 시점과 이유 기록 시점**을
구분한다. 이유를 실행 전에 남기지 못했으면 `사전 이유 미기록`이라고 쓰고,
나중의 설명은 `사후 추정`으로 분리한다. 모든 칸을 채우려고 이유를 만들어내지 않는다.

## 4. 매판의 고정 구조

`00판 시작 전` 다음에 `01판 종료 후`, `02판 종료 후`, …를 이어 쓴다.
각 절은 **해당 판 관측 종료 → 거래/장착 판단 → 다음 판 시작 명령**까지다.
구매는 끝난 판에 귀속하고 다음 판에 다시 세지 않는다.

각 절에는 다음을 같은 순서로 둔다.

1. **시작 공개 상태:** revision, 누적 활성 관측 시간, 이번 판 수입/길이,
   구매 전 자금, 표본 수입/잔액, 다음 판 길이, 완료 연구 수.
2. **선택 가능 상태:** 선행 충족 미구매 후보와 가격·현재 구매 가능 여부,
   모듈 재고·슬롯·용량·뽑기 비용. 긴 목록은 원본 state의 위치로 연결할 수 있다.
   구매 가능 수는 당시 열린 후보 수이며 후속 연쇄 전체의 구매 가능 수가 아니다.
3. **행동 표:** 명령 전 revision, 선택, 사전 이유, 실제 결과와 자원 변화.
4. **경계 종료 상태:** 실제 구매 수, 거래 후 잔액·표본·장착, 다음 행동.
5. **결과를 본 뒤 메모:** 기대와 차이 또는 정보 접근 변경. 관찰이 없으면 `추가 메모 없음`.

`next_round`의 수입은 다음 판 절에서 한 번만 집계한다. 슬롯 번호는 API의 0부터
시작하는 번호를 쓴다. 중간 종료·부분 관측은 `partial`과 실제 길이를 표시한다.
구매 실패·중복 뽑기·아무것도 사지 않음·모듈을 얻고도 안 씀을 누락하지 않는다.

## 5. 보존할 원본

증거 폴더에 아래 파일을 둔다. 원본은 제품 데이터나 플레이어 저장에 섞지 않는다.

| 파일 | 내용 |
|---|---|
| `config.json` | 실행에 적용된 전체 설정. 기본값 포함; 종료 report와 대조 |
| `transcript.jsonl.gz` | 순서가 보존된 공개 state, 사전 명령/이유, result, 후속 state, 종료 report |
| `report.json` | 정상 종료 시 받은 최종 집계. 실패로 없으면 부재 이유 명시 |
| 선택적 입력·로그 | dirty patch, 초기 상태, 엔진 오류 로그 등 재현에 필요한 자료 |

기존 실험과 호환되는 transcript의 사전 기록 형태는 다음과 같다. `decision`은 엔진으로
보내고 `reason`은 기록용으로만 보존한다. 엔진 프로토콜을 바꾸는 제안이 아니다.

```json
{"decision":{"action":"buy","id":"better_lens","revision":1},"reason":"저렴한 반경 강화를 먼저 시험하고 나머지 자금은 남긴다."}
```

바로 앞 `state`가 이 명령의 판단 입력이고, 다음 `result`/`state`가 결과다.
원본 state에서 목록을 삭제해 저장하지 않는다. 모델에 표시하는 정보만 줄일 수 있으며
그 필터를 실행 정보에 적는다. 화면 테스트라면 실제로 보인 화면과 입력이 별도 증거다.
현재 시뮬레이터는 `reason`이나 문서 생성을 자동 저장하지 않는다. 호출자가 이 순서를
기록해야 한다. 기존 report의 actions에는 성공 거래만 있으므로 실패를 확인하려면
transcript가 필요하다.

본문에 압축 해제한 transcript와 config/report 파일의 SHA-256을 적는다.
JSONL은 UTF-8이며 Python의 `gzip.open(path, 'rt', encoding='utf-8')`로 읽을 수 있다.
부분 기록이면 마지막 정상 revision과 누락 범위를 명시한다. 기록 공백을 숨기지 않는다.

## 6. 종료 후 집계와 해석

고정 요약값은 종료 이유, 완료 판 수/부분 판, 활성 관측 시간, 명시적 구매 수,
자동 보유 포함 연구 수, 수입·연구 지출·잔액·원장 오차, 최대 구매 묶음,
무구매 판 수, 뽑기/장착 수, 표본 수입·소비·잔액이다. 연구 수와 거래 수를 혼동하지 않는다.

구간 비교는 판 범위와 구매 귀속 기준을 적고 평균뿐 아니라 최대·무구매·3개 이상 구매
빈도도 함께 본다. 판 길이가 다르면 총수입과 초당 수입을 구분한다.
같은 시드라도 행동 차이로 이후 하늘이 달라질 수 있으므로 동일한 표본의 A/B라고 단정하지 않는다.

종료 후 해석은 **관찰 사실 / 해석 또는 가설 / 확인할 후속 실험**으로 분리하고 판 번호를
근거로 붙인다. 여러 업그레이드를 함께 산 뒤의 수입 증가를 하나의 효과로 단정하지 않는다.
합성 관측 시간은 사람의 완주 시간이 아니며, 속도·반경·훑기·선형 관측·감속·과충전의
실제 효율과 손맛은 이 모델로 확정하지 않는다. 제안을 승인된 설계 변경처럼 기록하지 않는다.

## 7. 저장 전 확인과 수정 이력

- 모든 실행 명령에 대응하는 사전 기록·응답이 있는가? 예외는 quit/EOF와 실제 중단이다.
- revision과 명령 순서가 맞으며 실패가 잔액·revision을 유지했는가?
- 판별 수입 합계, 구매 비용 합계, 마지막 잔액이 최종 report와 맞는가?
- 표본 거래, 자동 보유 항목, 부분 판과 종료 조건을 빠뜨리지 않았는가?
- 압축 해제·JSON 읽기·해시·상대 링크가 유효한가? 후속 해석이 당시 이유와 분리돼 있는가?
- 자신의 파일만 커밋하고 아카이브 지도에서 발견할 수 있는가? 저장소 완료 규칙도 따른다.

기록의 사실 오류는 수정할 수 있지만 문서 끝의 수정 이력에 날짜·수정 이유를 남긴다.
사전 이유와 원본 증거는 그대로 두고 정정 내용을 덧붙인다. 구조를 호환되지 않게 바꾸면
형식 버전을 올리고 변경점을 적는다. 이전 실행을 새 기준으로 조용히 덮어쓰지 않는다.
